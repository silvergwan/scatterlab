안녕하세요. 3116 최은관입니다. 제가 개발한 PlotFit 프로젝트를 바탕으로 답변하겠습니다.

PlotFit은 제타 사용자가 캐릭터 설정과 플롯 내용을 입력하면, 세계관에 맞는 대화 프로필을 생성해 주는 웹 도구입니다. Next.js와 TypeScript로 개발했고, OpenAI API와 Upstash Redis를 사용했습니다.

**첫 번째 질문은 프로젝트에서 겪은 기술적인 어려움과 해결 과정입니다.**

PlotFit을 개발하면서 어려웠던 점은 AI의 생성 결과를 애플리케이션에서 어떤 기준으로 받아들일지 설계하는 것이었습니다.

초기에는 원하는 출력 예시를 프롬프트에 넣고, 모델이 그 형식을 따라주기를 기대했습니다. 이후 출력 설계에 대한 질문을 받으면서, 생성 결과를 코드에서 검증하는 과정이 필요하다는 점을 알게 됐습니다.

먼저 모델에 JSON 객체 형식으로 응답하도록 요청했습니다. 그리고 Zod로 외형, 특이사항, 플롯 내 위치라는 세 필드의 타입과 필수 조건을 정의했습니다. 생성된 응답은 서버에서 검증하고, 검증을 통과한 결과만 화면에 반환하도록 변경했습니다. 스키마 검증에 실패하면 최대 두 번 추가 생성하도록 했습니다.

그런데 실제 테스트에서는 타입 검증을 통과해도 사용자가 입력한 취미가 빠지는 문제가 있었습니다. 이를 확인하면서 출력 형식과 내용의 정확성이 서로 다른 검증 대상이라는 점을 배웠습니다.

이후 입력을 외모, 성격, 배경, 기타로 나누고 항목별 설정 유지 여부를 전달하도록 바꿨습니다. 현재도 설정 누락 같은 한계가 남아 있어, 입력 사실이 결과에 보존됐는지는 별도 시나리오로 확인하고 있습니다.

이 경험을 통해 AI의 출력을 사용하는 서비스에서는 데이터 구조 검증과 실제 내용 검증을 함께 설계해야 한다는 점을 배웠습니다.

**두 번째 질문은 수업에서 배운 CS와 관련된 프로젝트 경험입니다.**

저는 서버리스 환경에서 요청 제한 기능을 구현하면서, 프로세스별 메모리와 공유 상태의 차이를 프로젝트에 적용했습니다.

PlotFit은 생성 요청마다 유료 API를 호출하므로 반복 요청을 제한해야 했습니다. 처음에는 서버 메모리의 Map에 IP별 횟수를 저장하는 방법을 검토했습니다.

하지만 서버리스 환경에서는 요청이 여러 인스턴스로 분산될 수 있습니다. 각 인스턴스가 자신의 메모리에만 횟수를 저장하면, 다른 인스턴스가 처리한 요청을 알 수 없어 제한 기준이 일관되지 않을 수 있습니다.

그래서 공용 저장소인 Upstash Redis를 선택했습니다. Redis는 키와 값으로 데이터를 관리하므로 IP를 키로 사용해 요청 횟수를 기록했습니다. INCR로 횟수를 증가시키고, 최초 요청에 EXPIRE로 60초의 만료 시간을 설정했습니다. TTL은 남은 제한 시간을 확인하는 데 사용했습니다.

현재는 IP당 60초에 다섯 번까지 허용하고, 여섯 번째 유효 요청에는 HTTP 429와 재시도 대기 시간을 반환합니다.

이 과정에서 여러 서버가 같은 상태를 판단해야 할 때는 저장 위치와 데이터 공유 방식을 먼저 고려해야 한다는 점을 이해했습니다.

**제가 만든 질문은 “생성 요청이 실패했을 때 서버와 화면에서 어떻게 처리했나요?”입니다.**

저는 실패 원인에 따라 서버의 응답과 사용자의 다음 행동을 구분했습니다.

먼저 입력 형식이 잘못됐으면 HTTP 400을 반환합니다. 이 검증은 Redis와 OpenAI 호출보다 먼저 수행해서, 잘못된 요청이 외부 서비스를 사용하지 않도록 했습니다.

요청 횟수를 초과하면 429를 반환합니다. Redis에 장애가 발생해 제한 상태를 확인할 수 없으면 503을 반환하고 유료 모델 호출을 중단합니다. 제한을 확인하지 못한 상태에서 생성을 허용하면 비용 통제가 어려워지기 때문입니다.

화면에서는 생성 중 버튼을 잠그고 스피너와 스켈레톤으로 진행 상태를 알립니다. 실패하면 오류 메시지와 재시도 버튼을 표시하며, 입력값은 남겨 사용자가 다시 작성하지 않아도 되도록 했습니다.

서버 동작은 Redis와 OpenAI를 대체한 자동 테스트로 확인했습니다. 잘못된 입력, 요청 제한 초과, Redis 장애 상황에서 불필요한 모델 호출이 발생하지 않는지 검사했고, 전체 테스트 83개가 통과했습니다. 화면의 로딩과 오류 후 재시도는 로컬 모의 응답으로 별도 확인했습니다.

이 경험을 통해 오류 처리는 예외를 잡는 것뿐 아니라, 서버 자원을 보호하고 사용자가 다음 행동을 할 수 있게 만드는 과정이라는 점을 배웠습니다. 감사합니다.
